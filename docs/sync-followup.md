# 同步完成后继续查课

当前代码位于 codex/langgraph-migration，尚未部署。LangGraph现在是标准依赖和唯一查询编排；部署需数据库包含0020_sync_followup（启动时也会幂等补列），不再需要引擎开关。普通查课保持原流程。只有支持完成通知的微信渠道能注册异步续答，其他渠道保持原提示。

## 用户行为

发送“同步一下课表，看看明天有什么课”：立即提交或复用后台同步任务，在同一数据库事务注册后续查询。只有注册成功才承诺同步成功后继续回复。成功通知包含同步结果和最新课程列表；失败通知给出分类原因，明确没有继续查课，不把旧课表作为同步后的答案。

首版只支持明确单日（可带上午/下午/晚上）或整周课程列表。天气、指定课程、下一节课、多日混合和含糊问句暂不注册，保持同步后再询问的提示。同一任务同一收件人只保留一条订阅；另一消息不会覆盖原问题，不承诺未注册的续答。冷却期复用已结束任务时不注册新通知，提示重新询问。

## 执行与持久化

消息入口 → Pydantic 计划（绝对日期/周一、时段、带时区请求时间、问题、版本）→ 任务和通知同事务提交 → 通知行 pending 等待任务结束与原消息处理完成 → claim 获取发送租约 → 核对原渠道身份、学校绑定版本和本次同步课表 → LangGraph query → render → 保存 delivery_text → 使用固定 client_id 发送 → sent。

“明天”在请求时冻结成绝对日期。输出日期标签依据续答时的当前时间，因此跨午夜后会显示正确的今天/明天；不会把目标日期向后移一天。请求有效期为24小时，超期明确提示重新询问。

续答图只有只读查询和 Pydantic 校验排版两个节点，不需要再请求模型，没有同步工具、自动重试、checkpointer/store 或 LangSmith tracing。数据库通知行负责持久等待和恢复；这不是把整张模型查询图 checkpoint 到数据库。

进程在查询期间退出：租约过期后重新执行只读查询。答案已经保存但发送失败：新进程读取同一正文，复用 client_id，不重复跑查询。失去租约的旧 worker 无法保存正文或发送；确认发送结果也受 lease_id 约束。沿用最多3次投递尝试。固定 client_id 用于降低重复投递风险，渠道对超时请求的最终处理仍无法保证绝对只发一次。

每次投递重试也重新核对绑定和课表归属；身份解绑/机器人失效会取消或结束投递。学校绑定变更、同步课表被删除、计划或结果不完整时不会发送旧的课程正文。现在没有legacy引擎开关。整包回退旧镜像后，新续答计划不会被旧代码执行；保留数据库记录，恢复新版后可继续处理有效期内任务。

## 依赖和迁移

0020只向 academic_sync_notifications 增加 followup JSONB 与 delivery_text TEXT，不变更原通知的唯一约束或同步任务状态机。新镜像默认安装LangGraph。发布前执行现有迁移/启动初始化流程。

回退保留新列并恢复旧镜像；旧代码可忽略额外列。不要为了代码回退执行数据库 downgrade，删除新列会丢失等待中的查询计划和缓存答案。

## 验证

2026-10-15：新旧引擎在候选环境各734 passed、41 skipped，包含37项新增续答测试。5项独立 PostgreSQL 集成测试验证事务回滚、订阅幂等、防覆盖、答案持久化后发送失败的恢复、租约抢占、绑定变更和幂等补列。Linux / Python 3.12 无网络容器中，两种引擎各230项通过，5项 PostgreSQL 测试跳过（已在独立本地 PostgreSQL 单独通过）。迁移的升降级和重复升级也已在临时 schema 验证。未调用真实学校接口或微信投递，尚未部署生产。

本地集成测试仅接受专用 localhost:55439 PostgreSQL；每次建立独立临时 schema 并在测试后清理。使用 XUSHI_FOLLOWUP_TEST_DSN 显式开启，默认跳过，CI提供隔离服务。
