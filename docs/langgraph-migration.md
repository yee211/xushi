# LangGraph 唯一编排与发布回退

## 当前实现

Agent 模型查询已统一使用 LangGraph，不再包含旧模型循环或 AGENT_ENGINE 开关。loop.py 仅保留稳定入口、共享协议辅助函数及熔断收尾；graph.py 是唯一模型查询编排实现。旧部署文件里的 AGENT_ENGINE 即便仍存在，也不会切换执行引擎。

图节点为 initialize → model → tools → model；最终回复进入 validate。异常、截断、预算或轮次耗尽进入 recover，优先保留已经校验的课程事实。模型最多调用4次，仍沿用同一请求时间预算。每次调用使用独立状态，不设置自动重试、checkpointer/store，不导出 LangSmith tracing。

同步提交及状态查询保留确定性业务入口；后台同步、通知投递、Redis会话和Pydantic课程排版保持现有服务实现。同步续答的持久等待由通知表负责，续答图执行只读 query → render，详见 [同步续答](sync-followup.md)。

旧的 _legacy_reply 已更名为 _fallback_reply，它是模型异常时的业务兜底，不是第二套模型工具循环。熔断开启或时间预算耗尽时走纯规则；熔断仍关闭且预算允许时，保留已有意图提取及润色行为。

## 安装与验证

requirements.txt 现在统一安装 langchain-core==1.4.7、langgraph==1.2.15 及配套固定依赖；Docker 默认安装同一清单，无需 INSTALL_LANGGRAPH 参数。requirements-langgraph.txt 仅作为旧开发安装命令的兼容别名，也引用同一清单。

```powershell
python -m venv tmp/langgraph-venv
tmp/langgraph-venv/Scripts/python.exe -m pip install -r server/requirements-dev.txt
tmp/langgraph-venv/Scripts/python.exe -m pytest server/tests -q -p no:cacheprovider
```

删除旧循环之前冻结了11组稳定版答案、模型请求摘要和熔断状态，保存在 tests/fixtures/agent_pre_langgraph_contracts.json。测试直接比对固定基准，不再保留旧执行代码；另外覆盖并发隔离、工具顺序、课程格式、超时恢复、轮次和预算限制。

CI 使用标准 requirements-dev.txt，包含独立 PostgreSQL 续答集成测试，不再运行双引擎矩阵。真实模型测试必须使用虚构数据，离线回归不代表真实模型准确率或渠道投递已通过。

## 发布与回退

本地迁移分支 codex/langgraph-migration；生产部署需构建新镜像，确认API/微信worker使用同一版本，并应用0020数据库补列或启动幂等初始化。现有生产服务不会因本地代码改变自动切换。

稳定版 GitHub 标签 pre-langgraph-20261014 指向 c5a7256。新版本已没有配置切回旧引擎的路径；需要回退时恢复保存的旧镜像/部署版本，并重建API及worker。保留数据库新增列，不执行数据库downgrade，避免丢失续答记录。旧镜像不会执行新续答计划，因此回退期间这些计划不会生成课程续答，需要后续恢复新版处理。

发布前保留原镜像、环境配置和数据库备份，验证普通查课、同步提交、状态查询及完成通知；不要在生产同时执行两套模型查询，避免重复工具副作用。

## 回复完成契约

统一编排出口保留原业务字段，新增固定的 `status`、`answer`、`task_id`，使用 Pydantic 校验。
模型请求使用 JSON 输出模式，普通最终回复要求同一结构；课程仍使用 `closing` 结构，由服务端渲染课程事实。
兼容旧供应商的纯文本回复，但同样必须通过执行证据和承诺校验，不能直接信任模型自报的状态或任务编号。
`pending` 仅由真实同步提交结果和任务编号产生；承诺完成后通知还要求通知登记成功，承诺查课还要求续答登记成功。
无后台任务支撑的“稍等、查好告诉你”最多触发一次纠正，继续使用原有四次模型调用上限和整轮预算。
课程事实已经可用时直接去掉无效提醒，不追加模型调用。统一出口同时拦截兜底润色或闲聊产生的空口承诺。
“课表是否最新、是否需要更新”等单纯状态问题直接读取同步记录，回复最近同步时间，并说明需要再次同步才能确认学校是否有新调整。
新增字段为兼容性扩展；现有渠道继续发送 `answer`，无需修改微信协议或数据库结构。


## 回复投递恢复

应用 `0021_message_reply`（或启动幂等初始化）后，微信最终回复在发送前写入 `channel_messages.reply_text`。
同一账户、同一消息重投时复用已保存正文和固定 client_id，不再调用模型、重新查询或消耗提问限流。
同步提交与通知登记已在同一事务中；入队后、回执持久化前崩溃时，也按原消息与原绑定查回同步任务，避免冷却期后重复提交。
同步完成通知在提交回执发送成功后投递；回执三次失败后也可继续发送最终结果，避免通知永久等待。
普通通知和查课续答都先持久化正文并核验租约，失去租约的执行者不发送。渠道重试继续沿用稳定 client_id，最终去重仍依赖微信服务端语义，不能承诺跨网络的严格恰好一次送达。
通知投递最多三次；凭证过期、解绑、重试耗尽会进入明确终态，不代表用户已收到消息。


## 审查修复：同步幂等与完成判定

`0022_sync_request_ids` 新增独立的 `academic_sync_requests` 消息映射表；通知回执路由可以变化，原消息与同步任务的关系保持不变。
映射与任务、通知在同一事务内保存，升级与启动初始化从现有通知回填可恢复的映射；已被旧版覆盖的历史消息编号无法反向恢复。
原消息在绑定条件变化后重投会要求发送新请求，不能悄悄提交另一身份的同步任务。
完成判定忽略辅助课程目录的成功，按每个核心工具及参数的最后一次结果检查失败；同一查询成功重试可恢复完成状态，不同日期仍各自检查。
“我帮你查询到了／查询完了／查询了课程”保留已验证结果；“我帮你查询一下／稍等”仍需执行或进入兜底。


## 审查补充：状态消费与兼容性

`status/task_id` 当前是内部判定、开发调试和评测契约。开发环境的 `/agent/debug/message` 返回这些字段；生产 weixin worker 发送 `build_agent_reply` 返回的正文；服务入口现已消费 `needs_input` 保存待确认事项，渠道投递仍不按状态分支。因此部分日期失败标记为 `failed` 本身不会改变用户收到的正文，也不表示渠道投递失败。
统一出口归一化回复正文；缺失或空白正文生成确定性失败提示，避免校验异常导致没有回复。模型有效的 `needs_input` 澄清不会被工具历史失败覆盖；显式业务错误、同步执行结果及无依据的工作承诺仍由服务端判定。
启动初始化目前仍扫描通知表回填映射，开销随全表行数增长；冲突时保留已有映射，遗留数据同一消息对应多个任务时按通知 `created_at` 优先选择较早记录，时间相同时顺序未定义。此兼容策略不能恢复曾被覆盖的消息编号；数据增长后应迁移为一次性回填。
